# Planning Copilot 실무 중심 제품 정리안

상태: 사용자 승인 (2026-10-04)

## 제품 판단

Planning Copilot의 중심은 "AI 에이전트 조직을 보여주는 것"이 아니라, 로컬 사업 기획자가 실제 공고와 자료를 바탕으로 제출 가능한 초안을 더 빨리 만드는 것이다.

### 한 문장 목표

공고·사업자료·사용자 메모를 근거로 연결해 기획서, 보고서, 콘텐츠 초안을 만들고, 사람이 검토한 결과만 로컬에 축적하는 개인 업무 도구.

### 기본 사용자 흐름

1. 프로젝트를 선택하거나 새 프로젝트를 만든다.
2. 공고문·양식·참고자료를 넣는다.
3. 이번에 해결할 업무를 한 문장으로 요청한다.
4. 시스템이 필요한 프로젝트 기억과 근거만 모아 한 번의 명확한 작업으로 처리한다.
5. 초안을 검토·수정하고 Markdown 또는 문서로 내보낸다.
6. 승인·결정·다음 액션만 프로젝트 기억에 남긴다.

항상 여러 AI 역할을 병렬 실행하는 대신, 한 명의 주 에이전트와 필요할 때 불러오는 역할별 프롬프트를 사용한다. 복수 에이전트는 단일 실행보다 품질·시간·비용이 실제로 개선된다는 평가 결과가 있을 때만 추가한다.

## 현재 코드에서 확인된 문제

- 탐색 메뉴가 20개가 넘고, 한 사업계획 흐름의 하위 단계가 각각 독립 탭이라 매번 어디서 시작할지 판단해야 한다.
- AI 사무국은 고정 템플릿 시뮬레이션으로 실행되지만, 모델 설정에는 Ollama·Gemini·GitHub Models가 별도 구현돼 있다. AI 사무국의 주 실행 흐름은 선택한 모델을 사용하지 않는다.
- Gemini API 키와 GitHub 토큰을 브라우저 localStorage에 저장한다. 공개·정적 웹으로 사용할 때는 비밀키 관리 경계가 적절하지 않다.
- 연결 허브는 Jira·Notion·Drive·Sheets API 연동이 아니라 프로젝트별 URL과 메모를 보관한다. "연결"로 오해하지 않도록 관련 링크로 이름과 위치를 낮춰야 한다.
- 사례 검색은 localStorage에 저장한 텍스트의 키워드 검색이다. 현재 구현을 임베딩 RAG나 자동 웹 리서치라고 설명하면 안 된다.
- CLI 하네스와 관제탑 사이에는 snapshot JSON 수동 가져오기가 있다. 안전한 MVP 경계이지만, 일상 업무의 중심 화면이 되기에는 작업 전환이 번거롭다.
- 사업기획 입력 폼, 문서 조립, 프로젝트 기억은 핵심 가치에 가깝지만 서로 분리되어 있어 같은 프로젝트 맥락을 반복 입력하게 만든다.

## 유지하고 강화할 기능

### 핵심 작업공간

- 공고문 분석과 파일 텍스트 추출
- 프로젝트별 사업 아이디어, 대상, 문제, 논리모형, 지표, 일정, 예산
- 프로젝트별 사례·공식 자료·결정사항 기억
- 사업계획서, 행정문서, 이메일, 콘텐츠 등 산출물 초안
- 검토 체크리스트, Markdown 내보내기, 승인 대기함
- Google Workspace 읽기 전용 Daily Briefing은 선택형 보조 기능으로 유지

### 모델 사용

- 기본: 설정 없이 동작하는 템플릿 모드임을 분명히 표시
- 실사용 로컬 추론: Ollama를 AI 작업 흐름에 연결
- 유료 모델 활용: 사용자가 자료를 점검한 뒤 외부 ChatGPT/Claude로 전달할 프롬프트 패키지 제공
- 클라우드 API: 브라우저 비밀키 저장을 제거하고, 실제로 안전한 로컬 프록시 또는 별도 서버 경계를 선택할 때까지 직접 키 입력·호출을 기본 기능에서 비활성화
- 모델 호출 실패, 비용, 입력 자료 범위, 생성 출처를 작업별로 기록

### 근거와 결과 품질

- 답변의 주요 주장과 자료 출처를 함께 보여주고, 출처가 없는 추론은 가정으로 표시
- 평가기준: 요구사항 충족, 근거성, 실행 가능성, 예산·일정 누락, 개인정보 위험
- 사용자의 수정·승인·보류 피드백을 다음 프로젝트 맥락에 반영
- 업무당 동시 진행은 최대 두 건으로 제한하고, 나머지는 대기열에 둠

## 통합 또는 1차 메뉴에서 내릴 기능

| 현재 기능 | 제안 |
| --- | --- |
| 질문 받기, 아이디어 인터뷰, 문제정의, 논리모형, 성과지표, 실행설계 | 하나의 프로젝트 기획 흐름 안에 단계형 섹션으로 통합 |
| 샘플 분해, 사례 모으기, 공고 해석 | 자료·근거 공간으로 통합하되 기존 데이터와 기능은 유지 |
| 시각자료, 서비스 블루프린트 | 산출물 편집기 안의 선택 도구로 이동; 사용 빈도 확인 전까지 삭제하지 않음 |
| Jira·Notion·Drive·Sheets URL 입력 | "프로젝트 링크"로 단순화; 미구현 API 연결을 암시하지 않음 |
| AI 사무국의 일곱 에이전트 시뮬레이션 | 역할은 전문 프롬프트로 유지하고, 화면은 작업 요청·진행·결과 중심으로 변경 |
| 관제탑 snapshot 수동 import | 최근 실행과 검토함 아래로 이동; 안정적인 로컬 브리지 없이 자동 읽기를 약속하지 않음 |
| Gemini·GitHub Models 키 입력 | 기본 화면에서 제거/비활성화; 안전한 비밀 관리 경로가 정해진 뒤 재도입 검토 |

"메뉴에서 내린다"는 것은 첫 정리 단계에서 화면의 우선순위를 낮추거나 다른 흐름에 합친다는 뜻이다. 기존 프로젝트 속성, 문서, 브라우저 저장값, 생성 산출물을 삭제하거나 마이그레이션 전에 덮어쓰지 않는다. 실제 데이터/코드 삭제는 사용 이력과 데이터 이전 검증을 통과한 뒤 별도 변경으로 한다.

## 제안 메뉴

1. **업무 홈**: 오늘의 브리핑, 진행 중 작업, 새 업무 요청, 최근 산출물
2. **프로젝트**: 공고·아이디어부터 논리모형·지표·실행계획까지 한 흐름으로 작성
3. **자료·근거**: 공고, 양식, 사례, 프로젝트 기억과 출처를 검색·검토
4. **산출물·검토**: 초안 편집, 문체/논리/일정/예산 점검, 승인·보류, 내보내기
5. **설정·연결**: Ollama, 데이터 백업, 프로젝트별 외부 링크, 읽기 전용 Workspace Briefing과 고급 도구

## 현재 AI 기술 흐름과 적용 판단

2026년 10월 현재 공식 제품 문서는 단순히 에이전트 수를 늘리기보다, 명확한 도구 경계, 필요한 맥락만 불러오는 컨텍스트 설계, 실행 추적과 평가, 민감 작업의 사용자 승인에 초점을 둔다. OpenAI Agents SDK 문서도 단일 전문 에이전트를 먼저 정의하고 필요에 따라 런타임, 도구, handoff, 검토로 확장하는 구조를 안내한다. Anthropic은 제한된 컨텍스트를 위해 검색 결과를 분리·압축하고 필요한 정보를 주 에이전트에 전달하는 context engineering을 설명한다. 따라서 본 제품은 "일곱 에이전트가 항상 협업"을 목표로 삼지 않는다.

OpenAI Agents API는 관리형 장기 실행/샌드박스 경로로 발전 중이며 모델·도구·컴퓨트 비용과 외부 데이터 경계를 추가한다. 로컬 우선과 비용 통제가 중요한 이 프로젝트의 기본 런타임으로 즉시 채택하지 않는다. 추후 API 연동 시에는 한 작업에 대한 품질 평가와 비용 상한을 먼저 측정한다.

Gemini 공식 키 안내는 운영 환경에서 브라우저에 API 키를 노출하지 말고 서버 프록시를 사용하라고 권고한다. 따라서 현재처럼 키를 localStorage에 보관하는 흐름을 강화하지 않고, 안전한 실행 위치를 결정하기 전까지 클라우드 키 저장을 기본 제품에서 내린다.

## 이번 정리에서 하지 않을 일

- 이메일 발송, Drive·Calendar·Sheets 쓰기, SNS 게시, 공문 제출
- 승인 없는 실행 또는 사람 대신 사업 결정을 확정하는 기능
- 사용자 자료를 외부 검색/API로 자동 업로드
- SaaS·다중 사용자 계정 체계로의 전환
- 새 의존성, 배포 구조, 클라우드 사업자 선택
- 기존 프로젝트·사례·승인 데이터의 자동 삭제

## 완료 판단 기준

- 첫 화면에서 다음 행동 하나를 바로 찾을 수 있다.
- 프로젝트 맥락을 한 번 저장해 여러 작업에서 재사용한다.
- 시뮬레이션과 실제 모델 호출을 사용자가 혼동하지 않는다.
- 주요 주장과 확인 가능한 출처가 구별되고, 미확인 가정이 표시된다.
- 산출물을 검토하고 수정한 뒤 안전하게 파일로 내보낼 수 있다.
- 비밀키가 브라우저 영구 저장소나 저장소에 남지 않는다.
- 기존 데이터는 유지되며, 메뉴 통합으로 사용 중인 기능이 사라지지 않는다.
